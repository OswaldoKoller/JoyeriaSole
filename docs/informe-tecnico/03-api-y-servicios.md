## 1. Convenciones de la API

### 1.1 Arranque, prefijo y registro de módulos

- Fastify 5.12 + `fastify-type-provider-zod` (Zod 4.6). `buildApp(env)` en `app.ts:75`. Validador y serializador Zod
  globales (`app.ts:91-92`): `body`, `querystring`, `params` **y** `response` se declaran con Zod en cada ruta; una
  respuesta que no cumpla su esquema de salida produce un error de serialización → 500 genérico.
- Prefijo único `API_PREFIX = '/api/v1'` (`packages/shared/src/api.ts:49`). Todo lo demás en `/api/*` no existe
  (404 JSON con formato estándar, `app.ts:148-156`). Fuera de `/api/` y con `WEB_DIST_DIR` presente, un `GET` sirve
  `index.html` (SPA, `app.ts:150`).
- Plugins, en orden (`app.ts:105-108`): `error-handler` → `security` (helmet, CORS, cookie firmada, rate-limit,
  hook CSRF) → `prisma` → `auth` (decoradores `authenticate`, `requirePermission`, `requireAnyPermission`,
  `sessionCookie`). Cada módulo es un plugin de rutas con su propio prefijo:

### 1.2 Formato de respuesta

| Caso                            | Forma                                                                                       | Dónde                                                                          |
| ------------------------------- | ------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ |
| Éxito con recurso               | `{ "data": T }`                                                                             | casi todas las rutas                                                           |
| Éxito con lista paginada        | `{ "data": T[], "meta": { "page", "pageSize", "total" } }`                                  | listados con `page/pageSize`                                                   |
| Éxito con avisos                | `{ "data": T, "meta": { "warnings": string[] } }`                                           | `POST /products`, `POST /products/:id/variants`, `PATCH …/barcode`             |
| Éxito con metadatos de lote     | `{ "data": T[], "meta": { "batchId" } }`                                                    | `POST /pricing/changes/approve                                                 | reject` |
| Alta rápida de ingreso          | `{ "data": detalle, "meta": { variantId, productId, warnings } }`                           | `POST /stock-entries/:id/items/quick`                                          |
| Sin contenido                   | `204` con cuerpo `null`                                                                     | `POST /auth/logout`, `POST /auth/change-password`                              |
| **Excepción**: sin sobre `data` | `{ "status": "ok", "database": "up" }` / `503 { "status": "degraded", "database": "down" }` | `GET /health`                                                                  |
| **Excepción**: binario          | bytes WebP (`image/webp`), SVG «Sin foto», `304` sin cuerpo                                 | `GET /products/:id/photos/:photoId`, `GET /products/variants/:variantId/cover` |
| Error                           | `{ "error": { "code", "message", "details"?, "requestId" } }`                               | todas (ver 1.3)                                                                |

`requestId` es un UUID v4 generado por petición (`genReqId`, `app.ts:78`; `requestIdHeader:false` para que el cliente
no pueda imponerlo) y se devuelve también en la cabecera `x-request-id` (hook `onSend`, `app.ts:94-101`).
Los listados de catálogos pequeños (categorías, atributos, roles, tipos de costo, motivos de ajuste, fotos) **no** se
paginan y devuelven todo.

### 1.3 Errores: códigos y mapeo HTTP

Códigos definidos en `packages/shared/src/api.ts:8-25` (`ERROR_CODES`, 12 valores). Jerarquía en `lib/errors.ts`
(`AppError` → `ValidationError`, `UnauthenticatedError`, `ForbiddenError`, `NotFoundError`, `ConflictError`,
`BusinessRuleError`, `PayloadTooLargeError`, `PasswordChangeRequiredError`).

| HTTP | `code`                      | Origen                                                                                                                                                                                    | Detalle                                                                                                                      |
| ---- | --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| 400  | `VALIDATION_ERROR`          | Zod (`hasZodFastifySchemaValidationErrors`) o `ValidationError` del servicio                                                                                                              | Zod: `details: [{ field: "body.email", message }]` (el `field` es `<contexto>.<ruta>`); servicio: mensaje + `details` libres |
| 401  | `UNAUTHENTICATED`           | sin cookie, firma inválida, sesión inexistente/revocada/vencida, usuario inactivo; credenciales inválidas                                                                                 | login falla con mensaje fijo «Correo o contraseña incorrectos»                                                               |
| 403  | `FORBIDDEN`                 | falta permiso; `Origen no permitido` (CSRF); acciones de dueño (cancelar ajuste ajeno, cancelar solicitud de precio ajena, capturar conteo sin ser operador); reglas de ADMIN en usuarios | mensaje en español; se registra `warn` con `userId`, `missing`, `url`                                                        |
| 403  | `PASSWORD_CHANGE_REQUIRED`  | sesión con `mustChangePassword=true` en cualquier ruta protegida por `requirePermission`/`requireAnyPermission`                                                                           | se evalúa **antes** que los permisos; solo `/auth/*` (que usa `authenticate`) funciona                                       |
| 404  | `NOT_FOUND`                 | recurso inexistente, ruta inexistente, `P2025` de Prisma                                                                                                                                  | también para foto de otro producto                                                                                           |
| 409  | `CONFLICT`                  | duplicados de negocio (`ConflictError`) y `P2002` genérico («Ya existe un registro con esos datos únicos»)                                                                                | `details` útil: `overlaps` (conteos), `variantIds`/`ids` (precios), `owner` (código de barras)                               |
| 413  | `PAYLOAD_TOO_LARGE`         | cuerpo > 1 MiB (JSON), archivo > 5 MB, `FST_REQ_FILE_TOO_LARGE`, `FST_FILES_LIMIT`, `FST_PARTS_LIMIT`, `FST_FIELDS_LIMIT`                                                                 | `PayloadTooLargeError` también si `Content-Length` declarado > 5 MB + 64 KiB                                                 |
| 422  | `BUSINESS_RULE_VIOLATION`   | regla de negocio (`BusinessRuleError`) y `P2003` (clave foránea)                                                                                                                          | `details` con bloqueadores (`blockers`), contadores, `status` actual                                                         |
| 422  | `STOCK_BLOCKS_DEACTIVATION` | desactivar producto/variante con stock > 0 (P-22)                                                                                                                                         | `details.variants: [{sku, quantity}]`                                                                                        |
| 429  | `RATE_LIMITED`              | `@fastify/rate-limit`                                                                                                                                                                     | mensaje fijo                                                                                                                 |
| 503  | `SERVICE_UNAVAILABLE`       | `P2034`, `P2028`, SQLSTATE `40P01`/`40001` (también en `meta.code` o `driverAdapterError.cause`)                                                                                          | cabecera `Retry-After: 2`; se registra `warn` (`error-handler.ts:23-40,76-84`)                                               |
| 500  | `INTERNAL_ERROR`            | cualquier otro error no controlado, incluidos errores de serialización de respuesta y violaciones de `CHECK` de la BD                                                                     | se registra completo en log con `requestId`; al cliente solo el mensaje genérico                                             |

Matices del manejador (`plugins/error-handler.ts`):

- Cualquier error 4xx propio de Fastify que no sea 413/429 (JSON mal formado, cuerpo vacío con `Content-Type: application/json`,
  `Content-Type` no soportado → **415**) se responde con el **mismo `statusCode`** pero `code: VALIDATION_ERROR` y mensaje
  «Solicitud inválida». Es decir, `415` y `VALIDATION_ERROR` coexisten (no documentado en `API.md`).
- Orden de evaluación: `AppError` → Zod → transitorios de BD (503) → `PrismaClientKnownRequestError` (P2002/P2003/P2025) →
  413 → 429 → otros 4xx → 500.
- Nunca se envía stack, SQL ni mensajes de Prisma. Prueba: `unit/error-handler.test.ts`, `integration/negative-stock-guard.test.ts`.

### 1.4 Paginación

- Parámetros `page` (≥ 1, por defecto 1) y `pageSize` (1–100, por defecto 25) coercidos desde la query; respuesta
  `meta: { page, pageSize, total }`. Paginación por **offset** (`skip/take` o `LIMIT/OFFSET`), sin cursor. `page` no tiene máximo.
- Excepción: `GET /inventory/counts/:id/scans` admite `pageSize` hasta **200** y por defecto **50**.
- Orden determinista con desempate por `id`: proveedores/usuarios/productos por nombre+id; ingresos/ajustes/conteos por `number desc`;
  movimientos por `id desc` (no por `createdAt`, que es el inicio de la transacción); auditoría `createdAt desc, id desc`;
  cambios de precio `createdAt desc, id desc`.
- Cada listado ejecuta `findMany` + `count` en una `$transaction([...])` por lote (lectura consistente de ambos).

### 1.5 Autenticación por cookie, sesión y autorización

- Login (`auth.service.ts:22`) crea una fila `sessions` con `tokenHash = SHA-256(token)` (el token es `randomBytes(32)` en base64url,
  256 bits, `lib/tokens.ts`); en la BD **nunca** queda el token. Cookie: nombre `sid` o `__Host-sid` si `COOKIE_SECURE` (producción
  por defecto), `httpOnly`, `secure` (según entorno), `SameSite=Strict`, `Path=/`, `expires` = ahora + 8 h, **firmada** con `AUTH_SECRET`
  (≥ 32 caracteres) (`plugins/auth.ts:118-143`). `SESSION_TTL_HOURS` solo admite `8`: sesión **fija**, sin extensión por actividad.
- Cada petición protegida resuelve la sesión con **una sola consulta SQL cruda** (`loadSessionUser`, `plugins/auth.ts:74-113`) que une sesión,
  usuario, roles y permisos y no trae `passwordHash`. Sin caché: revocaciones y cambios de permisos rigen en la petición siguiente.
  `lastSeenAt` se actualiza como máximo cada 5 min (fuera de transacción).
- Tres guardas, todas como **`preValidation`** (no `preHandler`) para que 401/403 se evalúen antes que el 400 de validación del cuerpo:
  `authenticate` (solo sesión; la usan `/auth/logout|me|change-password`), `requirePermission(...p)` (**todos** los permisos) y
  `requireAnyPermission(...p)` (**al menos uno**). Ambas últimas devuelven `PASSWORD_CHANGE_REQUIRED` si hay clave temporal.
- Rutas públicas: únicamente `GET /health` y `POST /auth/login` (verificado por el test `onRoute` de `security-hardening.test.ts`).
- Autorización siempre por **permiso**, nunca por nombre de rol. Catálogo de 24 permisos en `packages/shared/src/permissions.ts`.
  Roles semilla: `ADMIN` (todos), `INVENTORY_MANAGER` (Responsable), `SELLER` (`catalog:read` + `inventory:read`). Los roles son filas de BD y pueden
  ser personalizados (de ahí las reglas anti-escalada de `users.service.ts`).
- `getAuth(request)` (`plugins/auth.ts:52`) lanza 401 si se usa en una ruta sin guarda.
- Contraseñas: Argon2id (`@node-rs/argon2`, 19 MiB, t=2, p=1). Mínimo 10 caracteres (`PASSWORD_MIN_LENGTH`), máximo 200.

### 1.6 CSRF, origen y CORS

- CORS (`@fastify/cors`): se acepta sin `Origin` o con un origen de `CORS_ORIGIN` (lista separada por comas) ∪ origen de `FRONTEND_URL`;
  `credentials:true`; métodos `GET, POST, PUT, PATCH, DELETE`.
- CSRF: cookie `SameSite=Strict` **más** hook `onRequest` (`security.ts:55-62`): para `POST|PUT|PATCH|DELETE` con cabecera `Origin` presente y no
  permitida → `403 FORBIDDEN «Origen no permitido»`. **Sin** cabecera `Origin` la petición pasa (curl, pruebas); sigue exigiéndose la sesión.
  No se valida `Sec-Fetch-Site` (defensa en profundidad pendiente, ver §5). `Origin: null` se rechaza.
- Helmet: CSP `default-src 'self'`, `script-src 'self'`, `style-src 'self' 'unsafe-inline'`, `img-src 'self' data: blob:`, `object-src 'none'`,
  `frame-ancestors 'none'`, `upgrade-insecure-requests` si `COOKIE_SECURE`; HSTS 1 año + subdominios solo en `production`.

### 1.7 Límites de tasa (rate limits)

`@fastify/rate-limit` 11.2, almacén en memoria **por proceso** (válido para un único contenedor; no se comparte entre instancias).
Clave por defecto: IP (`request.ip`). Cada ruta con `config.rateLimit` propio tiene su **propio contador** (child store); el resto comparte el global.

| Ámbito                                                                          | Límite                                                     | Clave                                                  | Notas                                                         |
| ------------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------------ | ------------------------------------------------------------- |
| Global (todas las rutas sin configuración propia)                               | 300 / 1 min                                                | IP                                                     | `security.ts:47-51`                                           |
| `POST /auth/login`                                                              | `LOGIN_RATE_LIMIT_MAX` (10 por defecto, 1–10 000) / 15 min | IP                                                     | contador propio                                               |
| `POST /auth/change-password`                                                    | igual que login / 15 min                                   | IP                                                     | contador propio (distinto del de login)                       |
| `GET /health`                                                                   | 60 / 1 min                                                 | IP                                                     | `health.routes.ts:10`                                         |
| `GET /products/:id/photos/:photoId` y `GET /products/variants/:variantId/cover` | 3000 / 1 min                                               | **id de usuario** (hook `preHandler`, tras autenticar) | evita que una lista con decenas de miniaturas agote el global |
| `POST /products/:id/photos`                                                     | 40 / 1 min                                                 | IP                                                     | subida cara (decodifica y re-codifica)                        |

IP real: `trustProxy` = `false` por defecto; con `TRUST_PROXY_HOPS = n > 0` se confía solo en los `n` saltos propios contando desde el último
(`trustHops`, `app.ts:47`). `TRUST_PROXY=true` (antiguo) **aborta el arranque** (`config/env.ts:81-86`). Detrás de un proxy sin configurar `TRUST_PROXY_HOPS`
todos los usuarios comparten IP y el límite de login (10 / 15 min) se aplicaría a toda la tienda.

### 1.8 Cabeceras de caché y de seguridad en respuestas

- Hook `onSend` (`app.ts:94-101`): toda respuesta bajo `/api/` sin `Cache-Control` propio recibe `cache-control: no-store` (también errores y 404 de la API);
  añade `x-request-id`.
- Imágenes (`photos.routes.ts:110-128`): fotos `private, max-age=31536000, immutable` + `ETag "<sha256>"` (el id cambia con cada subida);
  portada y «Sin foto» `private, no-cache` + `ETag` (puede cambiar). Siempre `x-content-type-options: nosniff`, `content-security-policy: default-src 'none'; sandbox`,
  `content-disposition: inline`. `304` si `If-None-Match` coincide (acepta lista, `W/` y `*`). Lista blanca de `Content-Type` (`image/webp`, `image/jpeg`, `image/png`).
- No hay `Permissions-Policy` explícito.

### 1.9 Idempotencia: **no existe**

No hay cabecera `Idempotency-Key`, ni tabla de claves, ni índice único sobre `(referenceType, referenceId)` en el libro. Cómo se comportan hoy las
operaciones ante repetición:

| Operación                                                                                     | ¿Repetirla duplica efectos?                                                | Protección real                                                                              |
| --------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------- |
| Confirmar ingreso, aprobar/rechazar/cancelar ajuste, aprobar conteo, aprobar/rechazar precios | No                                                                         | bloqueo `FOR UPDATE` del documento + comprobación de estado → 2.ª llamada `422`              |
| Stock inicial                                                                                 | No                                                                         | `COUNT(movimientos)>0` bajo bloqueo de variante → `422 «El stock inicial ya fue registrado»` |
| Solicitud de precio                                                                           | No (por variante)                                                          | `409` si ya hay una `PENDING` (+ índice único parcial en BD según los tests)                 |
| `POST /inventory/exchanges`                                                                   | **Sí**: cada POST genera `randomUUID()` nuevo y aplica ambos movimientos   | ninguna                                                                                      |
| `POST /inventory/adjustments`                                                                 | Sí: crea otro documento `PENDING`                                          | ninguna (la aprobación es única por documento)                                               |
| `POST /stock-entries`                                                                         | Sí: crea otro borrador                                                     | ninguna                                                                                      |
| `POST /inventory/counts`                                                                      | No si hay variantes en común (409 por solapamiento); sí con otra categoría | lock asesor + solapamiento                                                                   |
| `POST /inventory/counts/:id/scan`                                                             | **Sí**: cada llamada suma 1 pieza                                          | `POST …/undo` deshace la última                                                              |
| `POST /products`, `POST …/variants`                                                           | Sí (nuevo SKU)                                                             | ninguna                                                                                      |
| `POST /users`                                                                                 | No                                                                         | email único → 409                                                                            |

### 1.10 Zona horaria y fechas

- Servidor y BD: `timestamptz` en UTC; la API serializa ISO 8601 con `Z` (`toISOString()`).
- «Día de negocio» = `America/La_Paz` (UTC−4 fijo, sin horario de verano) en `packages/shared/src/dates.ts`: `todayInLaPaz`, `documentDateBounds`
  (hoy − 30 días … hoy), `checkDocumentDate` (valida `documentDate` de ingresos, 400), `dayRangeLaPaz` (filtros `from/to` de ajustes: inclusive,
  `T00:00:00.000-04:00` … `T23:59:59.999-04:00`). Las fechas de documento (`documentDate`) se guardan como `@db.Date` en `T00:00:00Z`, sin hora.
- Auditoría: `from/to` son fecha-hora ISO **con zona** (`z.iso.datetime({ offset: true })`); no se aplica La Paz implícitamente.

### 1.11 Dinero, cantidades e identificadores

- **Dinero siempre como `string` decimal**, nunca `number`: `salePrice` 2 decimales (`"150.50"`, `"0.00"` = «sin precio»); costos unitarios 4 decimales (`"8.3333"`);
  importes del documento (costos adicionales, totales, `valueImpact`) 2 decimales. Entradas: regex estrictas (`^(0|[1-9]\d{0,9})(\.\d{1,2})?$` para precios de venta y
  costos adicionales; hasta 8 enteros + 4 decimales para precio de compra; tipo de cambio hasta 4 enteros + 4 decimales, > 0).
- Aritmética interna entera con `BigInt` en `packages/shared/src/costing.ts`/`pricing.ts` (unidades 1/10 000; centavos; reparto por mayor resto; mitad hacia arriba),
  idéntica en API y web. Salvedad: `pricing.service.ts:293` compara precios con `Number(...).toFixed(2)` (ver §5).
- Cantidades de stock: enteros (`Int` de 32 bits; `MAX_BALANCE = 2 147 483 647`). Topes de entrada: ajustes/cambios/conteos 1 000 000 por línea; ingresos 1 000 000; stock inicial sin tope (ver §5).
- Identificadores: UUID (v7) para entidades de negocio; `BigInt` autoincrementales (movimientos, auditoría, lecturas de conteo) serializados como **string**.
  Números legibles de documento: `ING-000001`, `AJ-000001`, `CNT-000001` (columna `number` autoincremental).

## 2. Catálogo completo de endpoints

**Total: 101 endpoints** de aplicación (más los `HEAD` automáticos de los `GET`). Distribución: health 1 · auth 4 · approvals 1 · users 7 ·
suppliers 4 · categories 5 · attributes 5 · products 13 · catalog/variants 1 · photos 7 · cost-history 1 · inventory 4 · adjustments 8 ·
exchanges 2 · counts 14 · stock-entries 9 · cost-types 3 · pricing 9 · audit 3.

**Convenciones de las tablas.** «Ref.» = archivo de rutas:línea del `app.<método>(` y, tras `→`, método de servicio:línea. Toda ruta protegida puede
responder además `401`, `403` (`FORBIDDEN` o `PASSWORD_CHANGE_REQUIRED`), `400` (Zod), `429` y `500`; no se repiten en cada fila salvo que haya matiz.
Las rutas con `:id` UUID devuelven `400` si el id no es UUID y `404` si no existe; solo se anota cuando hay otro 404 de negocio. «Audit» = `recordAudit(tx, …)` en la misma
transacción que el cambio. «Ledger» = escribe en `inventory_movements`/`inventory_balances`.

### 2.3 Usuarios y roles (`/users`)

(`422`). Ningún campo `passwordHash`/token se serializa (esquema `userSummarySchema`).

### 3.2 Servicio de libro de stock: `modules/inventory/stock-ledger.ts`

**Propósito.** Única operación genérica para modificar saldos de variantes: `applyStockChanges(tx, changes[]) → AppliedStockChange[]` (ADR-007). El llamador aporta la
transacción y debe grabar su propia auditoría en ella.

**Contrato de entrada** (`StockChange`): `variantId`, `type` (`MovementType`), `quantity` **con signo y ≠ 0**, `userId`, y opcionales `reason`, `notes`, `unitCost` (texto, 4 decimales),
`referenceType`, `referenceId`, `label` (para mensajes). Devuelve, en el **mismo orden** que `changes`, `{variantId, movementId: bigint, balanceBefore, balanceAfter}`.

**Algoritmo** (`stock-ledger.ts:62-135`):

1. Ordena los cambios por `variantId` (y por índice original dentro de la misma variante, para respetar el orden de aplicación).
2. **Fase de bloqueo**: para cada variante distinta, en orden, `SELECT id FROM product_variants WHERE id = $1 FOR UPDATE`. Bloquear la variante (y no solo el saldo) permite proteger
   también la **primera** vez, cuando aún no existe la fila de `inventory_balances`.
3. **Fase de aplicación**, por cambio y en el mismo orden:
   1. `INSERT INTO inventory_balances … VALUES (variante, 0, now()) ON CONFLICT DO NOTHING` (garantiza la fila).
   2. `SELECT quantity … FROM inventory_balances WHERE variant_id = $1 FOR UPDATE`.
   3. `planBalanceChange(antes, delta)` (función pura): `INVALID_DELTA` si no es entero o es 0; `NEGATIVE` si `antes+delta < 0`; `OVERFLOW` si `> 2 147 483 647`.
      Cualquiera lanza `BusinessRuleError` (422) con `details` (`variantId`, `balance`, `quantity`) y revierte **toda** la transacción del llamador.
   4. `INSERT inventory_movements` (`balanceBefore`, `balanceAfter`, `unitCost`, `referenceType/Id`, `reason`, `notes`, `userId`).
   5. `UPDATE inventory_balances SET quantity = after`.
4. Coste: **1 bloqueo por variante + 4 consultas por cambio** (≈5 por línea).

**Invariantes** (software + BD):

| Invariante                                                   | Quién la garantiza                                                                                                                                                           |
| ------------------------------------------------------------ | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Saldo ≥ 0                                                    | `planBalanceChange` (422) + `CHECK inventory_balances_quantity_check` (migración `20261106010000`); si el CHECK salta se responde 500 genérico (test `negative-stock-guard`) |
| `balance_after = balance_before + quantity` y `quantity ≠ 0` | `CHECK inventory_movements_balance_check` y `…_quantity_nonzero_check` (migración inicial)                                                                                   |
| Movimientos inmutables                                       | trigger `BEFORE UPDATE OR DELETE … prevent_append_only_change` (no cubre `TRUNCATE`)                                                                                         |
| Movimiento y saldo en la misma transacción                   | por construcción (usa `tx`)                                                                                                                                                  |
| Todo o nada en documentos de varias líneas                   | un `throw` revierte la `$transaction` del llamador                                                                                                                           |
| Orden de bloqueo `documento → variantes (id asc) → saldos`   | convención compartida; evita deadlocks entre operaciones que tocan las mismas variantes en distinto orden (test «mismas variantes en distinto orden no se interbloquean»)    |

**Quién lo usa** (3 módulos): `adjustments.service.ts:354` (`approve`, tipo `ADJUSTMENT`), `exchanges.service.ts:104` (`create`, `EXCHANGE_IN` + `EXCHANGE_OUT`),
`inventory-counts.service.ts:895` (`approve`, `COUNT_ADJUSTMENT`). Además `count-views.ts` importa `MAX_BALANCE` y `planBalanceChange`/`adjustments.service.ts` el planificador puro.

| Stock inicial     | `inventory.service.ts:164-214`              | Escritura directa; sin `referenceType`; verifica "sin movimientos previos"                                                                                                                                   |
| Baja de producto  | `products.service.ts:665`                   | `inventoryBalance.deleteMany` (borra saldos en cero)                                                                                                                                                         |
| Datos demo        | `apps/api/prisma/seed-demo.ts:245,339,474…` | Fuera de la API; crea movimientos/saldos directos                                                                                                                                                            |

**Lo que el ledger no hace (limitaciones actuales).** (a) No valida que variante/producto estén `ACTIVE` bajo el bloqueo; cada llamador lo comprueba **antes** y, salvo en `exchanges`
(que bloquea y luego lee), la comprobación ocurre sin bloqueo → ventana de carrera con una desactivación (ver §5, C-02). (b) No tiene clave de idempotencia ni
índice único por `(referenceType, referenceId, variantId, type)`. (c) No valida el signo según el `type` (p. ej. `SALE` positivo) — hoy no se usan los tipos de ventas. (d) No
reserva stock. (e) Usa `FOR UPDATE` (no `FOR NO KEY UPDATE`) sobre `product_variants`, que bloquea también inserciones con FK hacia la variante desde otras tablas.
(f) Tipos `LOSS`, `SALE`, `CUSTOMER_RETURN`, `EXCHANGE` existen en el enum pero **ningún código los escribe** en la Fase 1.

### 3.3 Servicios por módulo

#### Auth (`auth.service.ts`, 104 líneas)

- **Responsabilidades**: iniciar/cerrar sesión y cambiar la contraseña propia.
- **Reglas**: respuesta uniforme ante credenciales inválidas con verificación contra hash ficticio (`getDummyHash`, mismos costes de tiempo); sesión fija de 8 h; cambiar la clave revoca **todas** las sesiones;
  con `mustChangePassword` la nueva debe diferir de la temporal. Intento fallido audita `auth.login_failed` con el email en `metadata` y registra `warn` con el email en el log.
- **Transacciones**: login (sesión + `lastLoginAt` + audit) y logout atómicos; el audit del intento fallido va **fuera** de transacción (`this.prisma`).
- **Hallazgos**: no hay depuración de sesiones vencidas/revocadas (la tabla `sessions` crece sin límite); el bloqueo por fuerza bruta es solo por IP (no por cuenta).

#### Usuarios (`users.service.ts`, 252)

- **Reglas**: `assertCanTouch` (solo un ADMIN modifica a un ADMIN), `assertCanGrantAdmin` (solo un ADMIN asigna `ADMIN`; aplicado en `create` y `assignRoles`), `protectLastAdmin` (cuenta administradores activos
  tras bloquear el rol `ADMIN` con `FOR UPDATE`), no restablecerse la propia clave, desactivar o restablecer revoca sesiones. La cuenta nunca expone hash ni sesiones.
- **Bloqueos**: `roles WHERE code='ADMIN' FOR UPDATE` → `users … FOR UPDATE` (serializa operaciones que podrían dejar al sistema sin administrador; test de concurrencia).
- **Estado respecto a los informes**: la escalada de privilegios señalada como S-01/S-02 **está corregida** (código y tests `users.test.ts:591-683`).

#### Proveedores (`suppliers.service.ts`, 114) y tipos de costo (`cost-types.service.ts`, 102)

CRUD con auditoría antes/después; la unicidad (NIT) la impone la BD (P2002 → 409). Tipos de costo: los del sistema (`isSystem`) son inmutables; los nuevos usan código `CUSTOM_<SLUG>`.

#### Categorías (`categories.service.ts`, 202) y atributos (`attributes.service.ts`, 282)

- **Categorías**: máximo dos niveles (el padre debe ser raíz y estar activo); nombre único por nivel comparado en la aplicación (insensible a mayúsculas); no se desactiva con hijas activas; `setAttributes` es reemplazo
  completo y solo admite atributos activos (eje por defecto solo en atributos de lista). Sin `FOR UPDATE` en `update` (dos ediciones simultáneas podrían crear nombres repetidos; la BD no tiene un índice que cubra el nivel raíz).
- **Atributos**: los del sistema no se desactivan; no se desactiva uno en uso (cuenta cuatro referencias en paralelo); `VARIANT_AXIS` solo en listas; **renombrar un valor recalcula la etiqueta de cada variante**
  que lo usa con un bucle de `findUniqueOrThrow` + `update` por variante (N+1 dentro de la transacción de 30 s).

#### Productos y variantes (`products.service.ts`, 969 — el más complejo del catálogo)

- **Responsabilidades**: ficha de producto (con descripción, atributos, ejes), variantes con SKU correlativo, códigos de barras/proveedor, búsqueda unificada de piezas, estados y baja física, contadores de calidad.
- **Reglas de negocio impuestas**: ADR-001 (todo producto ≥1 variante; el stock es por variante); SKU único generado con `nextval('product_variant_sku_seq')` y verificación contra códigos de barras;
  Q-10 (el código del proveedor solo es código de barras si no pertenece a otra pieza; si choca se avisa y se identifica por SKU; con proveedor se conserva en `SupplierProduct`); P-22 (`assertNoStock`: no se
  desactiva producto/variante con stock >0, `STOCK_BLOCKS_DEACTIVATION`); B11 (`remove` solo sin movimientos, saldo ≠0, ítems de ingresos ni conteos); precio inicial solo con `prices:approve` y vía `recordInitialPrice`;
  el precio **no** se edita en `PATCH` (esquema `strict`); ejes solo antes de crear más variantes y sin historial de stock; combinación de variantes única; generar código solo en producto `ACTIVE`.
- **Bloqueos**: `products FOR UPDATE` (update/remove/axes/addVariant), `product_variants FOR UPDATE` (estado, mínimo, código), `inventory_balances … ORDER BY variant_id FOR UPDATE OF b` en `assertNoStock`.
  En `remove` se toman **saldos antes que variante** (orden inverso al del ledger → riesgo teórico de interbloqueo con una confirmación en curso; ver §5).
- **SQL crudo**: `nextval`, bloqueos `FOR UPDATE`, `assertNoStock`, bloqueo de saldos en `remove`.
- **Particularidades**: `createWithin(tx, …)` es reutilizado por el alta rápida de ingresos (`stock-entries`), por lo que **no** verifica permisos (quien llama debe haberlos comprobado); `ProductsService` se instancia
  en tres plugins distintos (productos, variantes, ingresos). Estado `DRAFT` del enum existe pero **ningún endpoint lo produce** (se crea `ACTIVE`; `PATCH` solo admite `ACTIVE|INACTIVE`).

#### Fotos (`photos.service.ts` + `image-processing.ts` + `photo-storage.ts`)

- Reglas: máximo 5 por producto (comprobado antes de procesar y de nuevo bajo bloqueo), una portada única (índice único parcial en BD), orden compacto, bytes en `product_photo_blobs` detrás de la interfaz
  `PhotoStorage` (cambiable por S3/R2 sin tocar el módulo; la implementación PostgreSQL participa en la transacción).
- `processPhoto`: firma de bytes → `sharp` con `limitInputPixels 30 000 000`, `failOn:'error'`, `.rotate()`, resize `fit:inside` 1200 px sin ampliar, WebP q82, `sha256` del resultado; semáforo de **2** trabajos concurrentes
  (`withSlot`), `sharp.cache(false)`, `concurrency(2)`.

#### Inventario (`inventory.service.ts`, 215)

- Lectura de saldos con **SQL crudo** (filtros/paginación en BD; escapa `\ % _` en la búsqueda) y kardex ordenado por `id desc`. `initialStock` impone: variante y producto activos, ningún movimiento previo, saldo 0.
  Es uno de los dos escritores **fuera** de `applyStockChanges`.

#### Ajustes (`adjustments.service.ts`, 419)

- Máquina de estados `PENDING → APPROVED|REJECTED|CANCELLED` con bloqueo `FOR UPDATE` del documento (`lockPending`). Al solicitar valida lo que ya se sabe (motivo activo, observación obligatoria si el motivo la exige, variantes
  activas, saldo no negativo/ni desbordado); al aprobar **revalida con el saldo vigente** y delega en `applyStockChanges`. El costo guardado en la línea es el `costPrice` de la variante en ese momento. Valorización con `BigInt`.
- `approve` lee las líneas con sus variantes **antes** de que el ledger bloquee las variantes: el costo y el estado `ACTIVE` pueden quedar desactualizados si hay una escritura concurrente (C-09/C-02).

#### Cambios de pieza (`exchanges.service.ts`, 197)

- Un cambio = dos movimientos atómicos con el mismo `referenceId`. Bloquea ambas variantes en orden de id **antes** de leerlas (correcto), exige variantes distintas y activas, delega en el ledger; no recalcula costos.
  El "documento" es virtual: no hay tabla de cambios, se reconstruye desde movimientos + auditoría (`load`). Sin idempotencia.

#### Conteos (`inventory-counts.service.ts` 1039 + `count-views.ts` 404 + `count-logic.ts` 100)

- **Lógica pura** (`count-logic.ts`, probada en `unit/count-logic.test.ts`): `reconcileCount` (esperado = vigente − movimientos posteriores al instante del conteo; diferencia = contado − esperado; resultado = contado + posteriores),
  `findScopeOverlaps`, `normalizeScanCode`, `needsRecount`, `finalCountOf` (el recuento prevalece).
- **Concurrencia**: lock asesor global `pg_advisory_xact_lock(680021)` en `create` y `start` (serializa la comprobación de solapamientos); `lockCount` (`FOR UPDATE`) en cada operación; `lockVariants` (`ORDER BY id FOR UPDATE`) en
  `start`, `close`, `approve` y, individualmente, en cada captura (`captureCursor`).
- **Cursores de conciliación**: `snapshotCursor` (último movimiento al iniciar), `countedCursor`/`recountCursor` (último movimiento al contar la pieza). La conciliación suma los movimientos con `id` mayor que el cursor
  vigente, de modo que un ingreso confirmado durante el conteo no genera falsa diferencia (ADR-014).
- **A ciegas**: las vistas `BLIND` se construyen sin campos de stock (`buildBlindDetail`); `REVIEW` solo desde `IN_REVIEW`. Es una protección **de contrato de API**: un usuario con `inventory:read` puede ver igualmente los saldos reales
  por `GET /inventory` mientras se cuenta (la ceguera es UX/proceso, ver §5).
- **Complejidad**: 14 operaciones públicas, `approve` ≈ 120 líneas con plan por ítem + ledger + actualización de N ítems; `scan` hace ~8 consultas por lectura; `close`/`approve` hacen bucles de `update` por ítem (N consultas).
  El CTE recursivo de categorías (`categoryTree`) no protege contra ciclos (la BD solo impide `parent_id = id`).
- **Auditoría**: solo transiciones de estado (`created`, `started`, `taken`, `first_closed`, `recount_closed`, `approved`, `cancelled`, `finding_regularized`); **las lecturas y correcciones manuales se guardan en
  `inventory_count_scans`, no en `audit_logs`**.

#### Ingresos (`stock-entries.service.ts`, 888)

- **Responsabilidades**: borradores de compra con moneda BOB/USD y tipo de cambio, ítems, costos adicionales, alta rápida de piezas, cancelación, confirmación y historial de costos.
- **Reglas**: la fecha del documento no es futura ni anterior a 30 días (La Paz); USD exige tipo de cambio (4 decimales, > 0) y `costs:read`; cambiar moneda/TC recalcula el costo en Bs de los ítems; el comprobante puede
  repetirse (entregas parciales, `relatedEntries`); confirmar exige `analyze()` sin bloqueadores (ingreso no vacío, ≥1 pieza recibida, reparto posible, sin variantes inactivas, diferencias esperado/recibido justificadas).
- **Costeo** (`packages/shared/src/costing.ts`, compartido con la web): precio en moneda del ingreso → Bs con `convertToBob` (redondeo 4 decimales, mitad hacia arriba) → reparto de costos adicionales por valor de compra con
  mayor resto (ADR-013/015/016). `unitTotal` pasa a ser el **último costo** (`cost_price`) de la variante (P-07 pendiente: no hay costo promedio ponderado).
- **Confirmar** (`confirm`, 727-848): transacción única con `lockDraft` (`FOR UPDATE` ingreso) → `analyze` → bloqueo de variantes recibidas **en orden de id** → por línea: saldo (crea/lee `FOR UPDATE`), chequeo de desbordamiento, movimiento
  `STOCK_ENTRY`, saldo, `cost_price`; luego actualiza cada ítem con sus costos congelados, estado `CONFIRMED` y auditoría con el detalle por ítem (incluye costo previo y nuevo). **No usa `applyStockChanges`** (duplica ~65 líneas).
- **Costo en consultas**: ≈7 consultas por ítem recibido (bloqueo, alta de saldo, lectura, movimiento, saldo, variante, ítem); un ingreso de 200 líneas ≈ 1 400 consultas dentro del tope de **30 s** (no usa los 60 s de los conteos).
- **Listado**: `list` carga `withDetails` (ítems + costos) de cada fila para calcular totales → coste proporcional a filas × ítems.

#### Precios (`pricing.service.ts`, 570)

- **Reglas** (ADR-018): el precio lo fija el cliente a mano; solicitudes `PENDING` (≤200 por lote, una pendiente por variante), aprobación/rechazo en masa **atómica**, cambio directo `ADMIN_DIRECT` y precio inicial `INITIAL`.
  Aprobar revalida que el precio vigente siga siendo el «anterior» de la solicitud (409 si no). El historial `price_changes` es inmutable (trigger) con `costSnapshot` del momento.
- **Bloqueos**: `lockVariants` (orden id) → `price_changes ORDER BY id FOR UPDATE`; en `cancel` primero la variante y luego la solicitud.
- **SQL crudo**: `DISTINCT ON (i.variant_id)` para el último ingreso confirmado de cada variante de la página (solo con `costs:read`).
- **Salvedades**: la detección «precio sin cambios» compara con `Number(item.newPrice).toFixed(2)` (no `BigInt`); `approve` no revalida que la variante siga `ACTIVE`; la auditoría `price.requested` guarda el
  `costSnapshot` aunque quien solicita no tenga `costs:read`.

#### Aprobaciones (`approvals.service.ts`, 29) y auditoría (`audit.service.ts` 33 / `audit-query.service.ts` 136)

- `ApprovalsService.pending` solo cuenta, y solo calcula cada cifra si la persona tiene el permiso de ese tipo.
- `recordAudit(db, entry, request?)`: acepta cliente normal o de transacción; toma `userId` de la entrada o de `request.auth`; guarda `ip`, `userAgent` (≤500) y `requestId`. `before/after/metadata` son JSON libre.
- Vocabulario de acciones registrado (57): `auth.login|login_failed|logout`, `user.created|updated|activated|deactivated|password_reset|password_changed|roles_updated`, `supplier.created|updated|activated|deactivated`,
  `category.created|updated|activated|deactivated|attributes_set`, `attribute.created|updated`, `attribute_option.created|updated|activated|deactivated`,
  `product.created|updated|activated|deactivated|deleted|axes_configured|photo_added|photo_cover_changed|photo_removed|photos_reordered`,
  `variant.created|activated|deactivated|min_stock_changed|barcode_assigned|barcode_generated|price_changed`, `price.requested|approved|rejected|cancelled`,
  `inventory.initial_stock|exchange`, `inventory_adjustment.requested|approved|rejected|cancelled`,
  `inventory_count.created|started|taken|first_closed|recount_closed|approved|cancelled|finding_regularized`,
  `stock_entry.created|updated|items_replaced|costs_replaced|item_quick_created|confirmed|cancelled`, `stock_entry_cost_type.created|updated|activated|deactivated`.
- Cada módulo escribe su auditoría **dentro** de la transacción de la operación (excepto el intento fallido de login). La tabla `audit_logs` es append-only por trigger (solo permite poner `user_id=NULL`).

## 4. Flujos de negocio de punta a punta

Notación: `Cliente → API`, `[tx]` = una única transacción de BD, `(audit)` = `recordAudit` en esa transacción. Los permisos entre corchetes son los exigidos por cada paso.

### 4.5 Cambio de pieza


### 4.6 Stock inicial

```
Responsable/Admin (inventory:initial-stock)
 ├─ GET /inventory?initialOnly=true      ← variantes con saldo 0 y sin movimientos (canInitialize)
 └─ POST /inventory/:variantId/initial {quantity>0, reason, notes?}
       [tx] FOR UPDATE product_variants → 404 · variante/producto ACTIVE (422)
            COUNT(inventory_movements WHERE variant) > 0 → 422 «El stock inicial ya fue registrado»
            INSERT balance (0) ON CONFLICT DO NOTHING → SELECT … FOR UPDATE → saldo ≠ 0 → 422
            UPDATE balance = quantity ; INSERT inventory_movements(INITIAL_STOCK, before 0, after quantity)   ← escritura directa, sin applyStockChanges
            (audit inventory.initial_stock)
       ← 201 {quantity}   — dos cargas simultáneas: una 201, otra 422; un ingreso confirmado posterior impide el stock inicial
```
